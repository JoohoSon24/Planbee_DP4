# Plan Bee 백엔드

**처음 실행한다면: [Live LLM 실행·화면 조작 순서](docs/LIVE_GUIDE.md)** — API 키 설정부터 시나리오 요청, PM 선택, 당사자 확인까지 순서대로 설명합니다.

## 실행 — 새 후보 생성·토론·PM 결정 앱

```bash
# .env에 OPENROUTER_API_KEY를 설정한 후 실제 LLM으로 실행
.venv/bin/python start.py --llm live --demo m4_t1_rescheduling

# API 비용 없이 같은 앱의 흐름을 확인할 때
.venv/bin/python start.py --llm mock --demo m4_t1_rescheduling
```

브라우저: **http://127.0.0.1:8000**. 프론트엔드는 [`front/Plan Bee Front.html`](<front/Plan Bee Front.html>)이며 서버 API에 연결됩니다. HTML 파일을 직접 열지 말고 위 명령으로 접속하세요. 서버 코드가 바뀌었으므로 기존 서버는 종료한 뒤 다시 시작해야 합니다.

현재 실행 목록에는 **Senario의 M4 시나리오 5개만** 표시합니다: T1 일정 이동, T2 재분배, T3 범위 축소, T4 복합 협상, T5 해결 불가능 충돌. `seed/catalog.yaml`이 공개 목록과 기본 시나리오를 정의합니다. 각 시나리오의 `seed/m4_t*/team.yaml`(초기 보드·카드), `feed.yaml`(변경 이슈), `source.md`·`board.png`(원문·이미지)를 보존했습니다. `mock_llm.yaml`은 오프라인 테스트용이며 `--llm live`에서는 사용하지 않습니다. 외부 Desktop 폴더에 의존하지 않고 실행할 수 있습니다. 기존 seed는 회귀 테스트/legacy 용도로 보존합니다.

T3의 Beta 이관·동반 잔여 작업 이관, T4의 단계별 분해·입력 의존성 재연결·선택 검증 생략을 후보 연산자로 추가했습니다. 명시된 Task 계약·검증 범위·동의 조건을 코드로 확인하며 Live 결과는 실험 기록과 구분해 보고합니다. 또한 공통 V2 정책상 T1·T4도 적용에는 PM 선택이 필요합니다. 원문과 실행의 차이 및 시간 정규화는 시나리오 설명에 표시합니다.

**내 역할 선택 → 업무 선택 → 채팅에 줄글로 이슈 입력 → 보내기** → 시간 안에 가능한 새 milestone 후보 생성 → 각자 카드로 토론 → **PM이 후보 1~3개 중 최종 결정** → 필요한 당사자 본인 확인 → Hive 최종 검증·적용 순서입니다. 후보가 하나라도 PM 선택 전에는 자동 적용되지 않습니다. **독립 평가 링크 생성**으로 동일 후보에 대한 사람 순위를 받아 공정성/카드 적합성의 rank-softmax CE, KL, Kendall τ-b를 비교할 수 있습니다. 평가는 선택한 역할과 동일한 본인 카드/공개 토론 정보를 사용하며, PM 운영 선택과 따로 저장합니다.

새 앱은 기본적으로 `planbee_v2_playground.db`를 사용해 이전 앱의 DB와 분리합니다(`PLANBEE_DB`를 지정하면 해당 설정 우선). 새 실행 기록은 **`runs/v2/live/` 또는 `runs/v2/mock/`**에 날짜·시간 파일명으로 저장합니다. 기존 `runs/live`, `runs/mock` 기록은 이동·삭제·덮어쓰기하지 않습니다. 테스트는 임시 폴더를 사용합니다. `PLANBEE_RUNS_DIR`을 직접 지정하면 그 경로가 우선합니다. 기존에 시작한 run을 새 서버에서 이어 실행하는 대신 새 run으로 시작하세요.

후보 탐색 기본값: 원시 조합 최대 500개, 검증 후보 최대 50개, 토론 후보 최대 10개, discussion 2라운드. 새 경로는 견적·생성·평가·토론·동의와 전송 재시도를 포함한 run 공유 호출 한도 **120회**, 처리 시간 한도 600초를 사용합니다. 생성 규모와 한도는 `POST /candidate-runs`의 `settings`로 조절할 수 있습니다. 환경변수 `PLANBEE_MAX_CANDIDATE_CALLS`로 기본 호출 한도를 바꿀 수 있습니다. 후보 50개는 목표 상한이며 충족할 수 없으면 실제 유효 후보 수와 탐색 종료 사유를 표시합니다. LLM은 생성/응답에 따라 비용이 발생합니다.

모델 설정: `.env`의 `PLANBEE_MODEL`은 개인 프록시 모델, `PLANBEE_GENERATOR_MODEL`은 생성 전용 모델입니다(생략하면 기본 모델 사용). 새 프롬프트는 [`prompts/README.md`](prompts/README.md)에 모았고, run 시작 시 내용과 hash를 고정합니다. MD 변경은 새 run에 반영됩니다.

최초 설치는 `python3.13 -m venv .venv` 후 `.venv/bin/python -m pip install -r requirements.txt`입니다. 기존 협상 경로는 `--negotiation-mode legacy`와 `/index.html`에서 사용할 수 있습니다. 아래 문서와 Report의 이전 결과는 legacy 구현 기록이며, 새 경로의 변경 내용은 [`docs/AGENT_CALL_FLOW.md`](docs/AGENT_CALL_FLOW.md)를 참고하세요.


구조·LangGraph·현재 Mock 데모 실행 결과를 그림으로 정리한 [백엔드 보고서](docs/Report.pdf)와 [데모별 시나리오 모음](docs/DEMOS.md)을 참고하세요. 보고서는 저장된 시나리오를 Mock으로 실행한 결과이며, Live LLM의 성능 평가와는 구분됩니다.

[전체 에이전트 호출 Figure와 호출별 설명](docs/AGENT_CALL_FLOW.md): Hive·개인 LLM·사람의 역할, 기한 회복 이후의 다자간 공정성 협상과 재동의·종료 경로를 두 장의 이미지로 정리했습니다.

[과제 #3 Cooperation – Agent Company 한국어 안내](docs/DEMOS.md#부록--과제-3-한국어-안내)는 데모 문서 부록에 포함되어 있습니다.

화면 상단에서 처리 단계 **01 입력·재견적 / 02 기한 회복 / 03 공정성 협상**, 협상 라운드, 데모 시연 순서를 구분해 볼 수 있습니다. 실행 중에는 서버의 실제 진행 상태를 조회하고, `runs/`에도 같은 단계별 섹션으로 대화와 제약 검증을 기록합니다. 02에서는 분할·전체 양도·미착수 업무 순서 변경을 협상할 수 있으며, 당사자 합의 뒤 Hive의 최종 제약 검증을 통과해야 반영됩니다.

**시나리오 설명**은 초기 일정 보드·마일스톤·위임카드·검색 가능한 Task 상세를 보여주는 화면입니다. 설명 화면의 데모 선택은 실제 실행 중인 판을 바꾸지 않습니다. 코드 수정 후에는 실행 중인 서버를 다시 시작하고 브라우저를 새로고침하세요 (`start.py`는 자동 reload를 사용하지 않습니다).

Report의 **11~14쪽**에는 discussion 확대도, 각 LLM 호출의 입력·출력, 분할 이외의 회복 전략과 Task 근거 전달을 추가했습니다. 기존 1~10쪽은 이전 구현의 기록이며 현행 동작은 후반 보충을 기준으로 보세요.

## 한 번 실행해서 모든 데모 둘러보기

Python 3.10 이상이 필요합니다. macOS의 `python3`가 3.9일 수 있으니 `python3 --version`으로 확인하세요. Python 3.13을 기준으로 가상환경을 만들면 시스템 Python과 패키지가 섞이지 않습니다. 기본은 매번 같은 결과가 나오는 Mock 모드입니다.

최초 1회 설치:

```bash
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

설치 후 실행할 때마다 입력하는 한 줄:

```bash
.venv/bin/python start.py --llm mock
```

브라우저가 자동으로 열립니다. 화면 위쪽 데모 메뉴에서 `demo1`, `demo2`, `demo3_cards`, `demo4_bundles`, `demo4_planbee`, `demo5_release`, `demo6_cross_region`를 바꾸고, 설정에서 여러 후보 중 업무를 맡길 기준도 `빨리 끝나는 쪽`, `배우고 싶은 사람`, `누적 부담 균형`으로 바꿔가며 **시연** 버튼을 눌러 보세요. 데모를 바꾸면 해당 데모의 초기 상태로 다시 시작합니다. 종료는 터미널에서 `Ctrl+C`입니다.

주소는 **http://127.0.0.1:8000**입니다. 상단 **시나리오 설명**에서 현재 데모의 초기 milestone 보드, 전원의 위임카드, 모든 Task의 description·산출물·의존관계를 볼 수 있습니다. **기록과 규칙 → 직접 누르기**를 선택하면 사람 확인을 하나씩 승인하거나 거절할 수 있습니다. PM 대기 시에는 **PM 확인 보기**에서 조건을 처리하면 다음 시연 단계가 열립니다.

| 데모 | 유형 | 브라우저에서 실행할 내용 |
|---|---|---|
| `demo1` | 6인 게임 개발 | 그림·코드 지연, 도움 조건, PM 검토 |
| `demo2` | Plan Bee M4 | 다른 역할로 분리, 통합 일정과 PM 조건 |
| `demo3_cards` | 카드 정보·권한 | 실행 가능한 시연 버튼으로 코드 분담과 확인 |
| `demo4_bundles` | 원자적 맞교환 | 시연 버튼으로 x/y 동시 교환; 수동 확인도 지원 |
| `demo4_planbee` | 맥락·휴가·부담 | 독립 API 분리, 휴가 일정과 누적 부담 |
| `demo5_release` | 복잡: 8인·20 Task·4 milestone | 5라운드 다자간 합의 → QA 지연 복구 → 릴리스 검사 |
| `demo6_cross_region` | 복잡: 10인·24 Task·4 milestone | 위반 제안 차단·최대 라운드 → 4건 분할·맞교환 묶음 → 재검사 |

복잡한 데모로 바로 시작하려면:

```bash
.venv/bin/python start.py --demo demo5_release --llm mock
# 또는
.venv/bin/python start.py --demo demo6_cross_region --llm mock --port 8006
```

데모 3의 누락된 버튼 라벨과 묶음 데모의 비어 있던 실행 단계를 보완했습니다. 모든 데모는 같은 상단 메뉴에서 전환·초기화할 수 있습니다. 데모를 전환하면 현재 판이 선택한 데모의 초기 상태로 바뀝니다. 종료된 데모는 **처음부터**로 다시 실행합니다.

모든 데이터와 인물·작업량은 시연용 합성 자료입니다. Mock의 거절·수정안 대본은 같은 실행을 재현하기 위한 것이며 실제 LLM의 협상 품질을 측정한 결과는 아닙니다.


### 마감부터 맞추고, 그다음 공정성 협상

마감 복구 단계에서는 원 Task 전체도 다시 분해할 수 있습니다. 예를 들어 4일짜리
‘상태 전이·계약 검증’을 코어 2일과 정상/실패 검증 각 1일로 나누고, 검증 둘이
코어 뒤에 병렬로 시작하도록 제안할 수 있습니다. 총 범위는 유지하며 코드가 실제
일정을 검증하고 당사자가 새 분담안 전체에 동의해야 적용됩니다. 검증·합의된
마감 배분을 먼저 저장한 뒤 공정성을 논의하며, 공정성 협상이 실패해도 그 배분은 유지합니다.

기본 협상 한도는 **15라운드**, 설정 범위는 **1~50라운드**입니다. 기존 DB에
저장된 5라운드 등은 **기록과 규칙 → 최대 협상 라운드**에서 바꿔 주세요.
PM 대기 중인 협상은 한도를 늘린 뒤 **라운드 설정 반영하고 협상 재개**를 누르면
기존 대화와 같은 `runs/` 파일에 이어집니다. 실패 시연용 데모 6은 의도적으로
3라운드를 유지합니다. ‘협상 한도 내 합의 실패’는 불가능함을 증명한 결과가 아닙니다.

실제 LLM을 선택하려면 `.env`에 OpenRouter 키를 설정한 뒤 다음처럼 실행합니다. Live 모드도 데모 메뉴에서 데모를 바꿀 수 있습니다.

```bash
.venv/bin/python start.py --llm live
```

앱의 전체 기본 모델은 `.env`의 `PLANBEE_MODEL`로 지정할 수 있습니다. 기존 값은 자동으로 바꾸지 않습니다. 비교 검증에서는 `openai/gpt-4.1`의 데모 5 초기 분할 합의·제약 통과를 확인했으며, 이는 한 번의 실행 증거입니다. 별도 DB에서 모델을 비교하려면 다음 명령을 사용합니다.

```bash
.venv/bin/python scripts/debug_live_negotiation.py --demo demo5_release --rounds 15 --model openai/gpt-4.1 --all-phases
```

이 디버그 실행은 사람 확인을 자동 처리하며 `runs/live/`, `eval/live_debug/`에 기록합니다. 사용자 DB는 변경하지 않습니다.

현재 Mock 버전의 데모 전체를 재실행하고 실행 기록과 그림 보고서를 갱신하려면:

```bash
PLANBEE_LLM=mock .venv/bin/python run_all_demos.py
```

다른 시작 데모나 포트를 지정할 수 있습니다: `.venv/bin/python start.py --demo demo4_planbee --port 8004`.

일정이 밀렸을 때 사람마다 하나씩 있는 프록시(AI)들이 서로 묻고 답해서 누가 무엇을 떠안을지 정하고, PM 에게는 규칙 안에서 못 푼 것만 올리는 서버입니다. 화면(`web/index.html`)은 프로토타입 "Handoffs 세 화면"을 이 서버에 연결한 것입니다.

- 기존 데모 1·2, 정보·권한 비교 데모 3, Plan Bee 프로젝트 데모 4와 별도 묶음 맞교환 예제가 들어 있습니다.
- 기본은 Mock 프록시라 API 키 없이 돌고, 매번 같은 결과가 나옵니다.
- 실제 LLM(OpenRouter)으로도 돌릴 수 있지만, 프롬프트는 아직 다듬지 않았습니다.

## 수동 실행과 API 문서

위의 `.venv/bin/python start.py`가 기본 실행 방법입니다. 서버를 직접 띄우거나 개발 자동 새로고침이 필요하면 의존성을 설치한 뒤 아래 명령을 사용합니다.

```bash
.venv/bin/python -m uvicorn app.api:app --reload
```

`http://localhost:8000`은 화면, `http://localhost:8000/docs`는 API 문서입니다. DB는 처음 켤 때 자동으로 만들어집니다.

## 데모 3: 객관적 여건과 위임 권한의 네 조건

사람은 4명, 사건은 하나입니다. Mia의 기능 구현이 3일에서 4일로 늘어 독립 모듈 1일을 Jun 또는 Sol에게 요청합니다. Jun은 기존 업무 4.5일이라 추가 수락이 불가능하고, Sol은 2일이라 가능합니다. Ara는 결과물을 받아 테스트합니다.

| 조건 | 프록시의 객관적 여건 정보 | 새 업무 자동 수락 권한 |
|---|---|---|
| 1 위임 카드 없음 | 없음 | 없음 (0일) |

### LLM이 판단할 업무 맥락

각 task에 `context`를 넣었습니다: 목적, 관련 파일, 산출물, 분리 경계, 완료 기준입니다. `PATCH /tasks/{id}/context`로 수정할 수 있습니다.

| 업무 | 제공한 맥락 | 판단해야 할 것 |
|---|---|---|
| 협상 재개와 증거 로그 | 상태 전이는 공통 트랜잭션이지만 읽기 전용 조회는 스키마·픽스처를 넘길 수 있음 | 읽기 전용 증거 조회 API를 독립된 산출물로 분리할 수 있는가? |
| 일회성 승인·서명 키 교체 | 키와 감사 기록이 함께 바뀌어야 이중 확정을 피함 | 분리하면 일관성이 깨지므로 그대로 두어야 하는가? |
| 배포 점검·사용자 테스트 등 | 필요한 URL, 선행 결과, 체크리스트, 동의 범위 | 무엇을 받아야 시작할 수 있고 무엇을 넘겨야 하는가? |

Live LLM은 `splittable`, `rationale`, 구체적 조각·인수인계 자료를 답합니다. `splittable=false`이면 **분리를 강요하지 않고** PM의 범위 조정·약속 재검토 경로로 보냅니다. 맥락이 있는 업무의 LLM 응답이 실패해도 단순히 일수를 잘라 대신 제안하지 않습니다. Mock은 시연 대본과 명시적 힌트를 사용하며, Live 입력에서는 Mock용 `splittable_hint`를 제외합니다.

`POST /tasks/resume/analyze-split` 또는 `/tasks/signoff/analyze-split`에 `{"days":0.5}`를 보내면 배정을 바꾸지 않고 판단만 볼 수 있습니다. 기본 Mock에서 보이는 것은 대본이며 실제 LLM 추론이 아닙니다.

### 두루뭉술한 위임 카드

- 주호: “최근 배포와 긴급 수정이 계속돼서 **나 너무 바쁨**. 작은 API라도 새로 맡기기 전에 확인해 주세요.”
- 정민: “**11/19~20 휴가**라 그때는 일을 못 해요. 그 전 독립 API는 1.5일까지 맡겨도 괜찮아요.”
- 여경: “재개 로직은 내가 마무리하고, 독립된 조회 부분만 맡겨 주세요.”
- 나정: “모호한 요구는 먼저 물어보고 사용자 동의서를 함부로 나누지 마세요.”

`POST /people/{id}/card/interpret`에 `{"note":"...","week_start":"2026-11-16"}`를 보내면 LLM이 **검토용 초안**을 돌려줍니다. 이 호출은 카드나 일정을 변경하지 않습니다. 사람이 질문·기간·한도를 확인하고, 같은 원문 note와 `policy.approved=true`를 `PUT /people/{id}/card`에 보내야 적용됩니다.

“바쁨”만으로 주당 일수를 임의로 정하지 않습니다(`busy=true`, `weekly_limit=null`). 새 업무는 카드 숫자 한도 안이어도 본인 확인을 받습니다. 명확한 휴가는 `start_date`, `end_date_exclusive`의 ISO 날짜를 코드가 주간 좌표로 변환합니다. 예를 들어 11/19~20은 11/19 시작, 11/21 미포함 종료이며 월요일=0 기준 `[3,5)`입니다. 휴가와 겹치는 미완료 업무는 **작업 전체를 휴가 뒤로** 미룹니다(하루 안에서 쪼개는 선점 실행은 아님). 이미 완료한 작업은 이동하지 않습니다. 가용량·주간 한도도 함께 검사합니다.

메모 원문만 바꾸면 해석은 미확인 상태가 되어 새 수락에 확인이 필요합니다. 기존에 확인된 휴가 제약은 새 해석 승인 전까지 보존합니다. 숫자 한도·역할·거부 태그는 자유 메모로 자동 확대하지 않습니다.

### 공정성의 정의와 선택 기준

`Person.notes.past_effort`는 **이번 주 업무와 중복되지 않는 최근 누적 작업량(일)**입니다. 이번 주에는 완료한 일도 한 번 포함합니다.

```text
개인 부담 = 최근 누적 작업량 + 이번 주 배정된 작업량
공정성 점수 = 팀 개인 부담들의 분산 (작을수록 더 고름)
```

마감 검사에서 위험이 없더라도 `fairness_gate`가 종료 전에 부담을 확인합니다. 팀의 부담 범위가 기본 기준 3일 이상이고, 같은 역할의 낮은 부담 후보와 높은 부담 담당자 사이가 2일 이상이면 연결된 미완료 업무를 찾아 LLM에게 나눌 수 있는지 묻습니다. 후보 응답 후 Hive는 기한 위험이 생기는 안을 제외하고 부담 분산이 가장 낮은 수락안을 고릅니다. 독립 조각이나 안전한 후보가 없으면 기존 배정을 유지합니다.

`fair`는 같은 요청의 가능한 후보들을 비교해 **마감 위험이 없는 후보 → 전달 지연이 없는 후보 → 부담 분산이 작은 후보 → 소요 일수가 짧은 후보** 순으로 선택합니다. 전역 최적 스케줄러가 아니라 한 요청의 후보들 사이를 고르는 방식입니다. 휴가·능력·동의·권한을 무시하면서 수치를 똑같이 맞추지는 않습니다. LLM 프롬프트에도 자기 누적 부담을 고려하고 다른 사람의 사정을 추측하지 않도록 넣었고, 최종 팀 전체 비교는 코드가 계산합니다. 묶음 이동 미리 보기에도 부담 점수를 표시합니다.

| 같은 시나리오 | 선택 | 조회 API 일수 | 사람 확인 | 부담 분산 | 최대-최소 | 제출일 초과 |
|---|---|---:|---:|---:|---:|---:|
| fast | 주호 | 1 | 2 | 10.796875 | 9 | 0 |
| fair | 정민 | 1.5 | 1 | 6.125 | 6.5 | 0 |

정민은 휴가 전인 수요일 오전까지 완료할 수 있습니다. 더 느려도 기존 부담이 낮아 전체 부담이 더 고르게 됩니다. 이 결과는 동일 사건·카드·경력·업무를 고정한 **Mock 비교**입니다. 주호의 실제 과로 또는 정민의 실제 여유를 측정한 결과가 아닙니다.

### 실제 LLM 확인

API 키가 `.env`에 설정되어 있다면:

```bash
python run_demo4.py --live-check
```

Mock 비교 후 실제 LLM으로 분리 판단 2건과 카드 해석 2건만 확인하며, 결과를 일정에 자동 반영하지 않습니다. `live_checks.json`, `live_meta.json`에 응답·모델·실패 수를 기록합니다. 전체 협상 자체를 Live로 돌리려면 서버의 `PLANBEE_LLM=live`를 사용합니다(별도의 변동 가능한 실행).

개발 중 실제 호출에서 조회는 분리 가능, 승인·서명은 분리 불가라고 답했습니다. 첫 카드 해석은 휴가 좌표를 잘못 썼기에 `live_checks_initial.json`을 보관했고, ISO 날짜를 코드가 계산하도록 보완했습니다. 수정 후 날짜는 맞았지만 휴가 메모까지 busy로 보수적으로 분류하는 경우가 남았습니다. 그래서 **해석 초안과 사람이 확인한 정책을 구분**하며, 작은 호출 확인만으로 일반적인 추론 정확도나 성능 개선이 입증됐다고 주장하지 않습니다.

새 JSON 열(`task.context`, `card.policy`)은 기존 DB의 다른 내용을 지우지 않고 추가합니다. 예상하지 못한 스키마 차이는 데이터를 삭제하는 대신 오류로 중단합니다.

## 묶음 이동: 맞교환·다수 분배·연쇄 교환

`app/bundles.py`는 여러 이동을 한 제안으로 검사하고 **모두 확정하거나 모두 취소**합니다. 기존 기록 협상은 한 조각을 자동 제안하고, 새로운 묶음 기능은 사용자가 명시적으로 입력한 여러 이동을 처리합니다. LLM이 스왑이나 분배 계획을 자동 생성하는 기능은 아직 없습니다. 기존 화면에는 묶음 편집기를 추가하지 않았고 API(`/docs`)와 CLI로 사용할 수 있습니다.

### 즉시 실행하는 사례 네 개

```bash
PLANBEE_LLM=mock python run_bundle_demo.py --case all
```

`--case swap`, `split`, `chain`, `reject`로 하나만 실행할 수 있습니다. 메모리 DB를 사용하며 실제 화면의 DB는 바꾸지 않습니다.

| 사례 | 실행 내용 | 결과 |
|---|---|---|
| swap | Mia의 x 2일 ↔ Jun의 y 2일 | 한쪽만 넘기면 7일로 초과. 묶음이면 각 5일로 가능. 두 사람 동의 후 함께 확정. |
| split | Mia의 x 2일 중 0.5일씩 Jun·Sol에게 | Mia 1일 + Jun 0.5일 + Sol 0.5일. 전부 끝나야 Ara의 테스트 진행. |
| chain | Mia x → Jun, Jun y → Sol, Sol z → Mia | 세 사람 동의 후 함께 확정. |
| reject | 맞교환 중 한 사람이 거절 | 다른 사람이 먼저 동의했어도 두 배정 모두 원래대로 유지. |

`eval/bundles/RESULTS.md`, `results.json`, 사례별 JSON에 제안 전·동의 대기·각 확인 직후·완료 상태를 저장합니다. 일정·권한 검사는 코드이며 LLM 호출은 없습니다.

### 실제 HTTP API에서 맞교환 실행

별도 묶음 예제(`demo4_bundles`)는 x/y 맞교환을 바로 재현할 수 있는 초기 판입니다. 데모 3의 네 조건 실험은 그대로 유지됩니다.

```bash
PLANBEE_DEMO=demo4_bundles PLANBEE_LLM=mock .venv/bin/python -m uvicorn app.api:app --reload --port 8003
```

`http://localhost:8003/docs`에서 아래 순서대로 실행합니다. 이미 실행 중인 서버를 쓴다면 먼저 `POST /demo/select`에 `{"demo":"demo4_bundles"}`를 보내면 같은 초기 판이 됩니다. 이 선택은 현재 판을 초기화합니다.

1. `POST /bundles/preview`에 아래 JSON을 보냅니다. 배정을 바꾸지 않고 전체 일정, 받는 작업량 합계, 필요한 당사자 확인을 보여 줍니다.
2. 같은 JSON으로 `POST /bundles`를 호출합니다. 이때도 기존 배정은 바뀌지 않습니다.
3. 응답의 `waiting_for`에 담긴 각 ID에 `POST /confirmations/{id}`로 `{"ok":true}`를 보냅니다.
4. `GET /bundles/{묶음 id}`가 `outcome: committed`가 되면 두 이동이 함께 적용된 것입니다.

```json
{"transfers":[{"task":"x","to":"jun"},{"task":"y","to":"mia"}]}
```

하나라도 `{"ok":false}`면 `cancelled`가 되고 미처리 확인도 취소됩니다. `POST /bundles/{id}/cancel`로 대기 중인 제안 전체를 직접 취소할 수도 있습니다.

### 조각의 양과 권한 검사

`amount`를 생략하면 작업 전체를 옮깁니다. 지정하면 **현재 원담당자 견적 기준의 작업량**을 넘깁니다. 양은 유한한 양수이며 0.5일 단위입니다. 수신자의 실제 소요 일수는 경력 계수로 다시 계산하므로 전체 예상 일수는 늘어날 수 있습니다. 제출자는 각 조각이 독립적으로 수행 가능함을 전제로 입력해야 하며 코드는 업무 내용의 독립성을 판단하지 않습니다.

분배 예시(분배용 초기 판은 CLI의 `--case split`에서 구성):

```json
{"transfers":[{"task":"x","to":"jun","amount":0.5},{"task":"x","to":"sol","amount":0.5}]}
```

- **원담당자**는 내 작업을 넘기는 데 항상 동의해야 합니다.
- **수신자**는 묶음에서 받는 일수의 **합계**가 `auto_days`를 넘으면 본인 확인을 받습니다. 내보내는 일수를 빼서 권한 한도를 피하지 않습니다. 한도 이내라면 카드가 수락을 위임한 것으로 처리합니다.
- `refuse_tags`의 업무는 제안 자체를 거부합니다. 역할이 다른 사람에게는 보낼 수 없습니다.
- 한 사람이 여러 역할로 참여하면 묶음 전체에 대해 확인 한 번을 받습니다.
- 모든 사람이 동의하기 전에는 작업·전달 약속을 변경하지 않습니다. 한 명의 거절은 전체 취소입니다.
- 마지막 동의 직전에 일정·카드·규칙·인물 정보의 변경 여부와 전체 일정 조건을 다시 확인합니다. 바뀌면 `invalidated`로 끝내고 새로 제안해야 합니다.
- 작업과 전달 약속의 저장은 하나의 DB 트랜잭션으로 처리합니다. HTTP 변경 요청을 직렬화하고, 저장 실패 시 마지막 동의와 모든 배정 변경을 되돌립니다.

분배할 때 원래 작업 ID는 **작업량 0의 완료 대기점(`milestone`)**으로 남고, 남은 부분과 넘긴 조각이 모두 끝나야 완료됩니다. 기존 후속 작업은 이 지점을 계속 기다리므로 일부 조각만 끝났다고 먼저 시작하지 않습니다. 원래 선행 작업의 의존관계도 모든 조각에 복사합니다.

### 현재 범위와 제한

아직 시작하지 않은 같은 역할의 작업만 대상으로 하고, 제안 하나는 최대 32개 이동입니다. 완료·가약속·완료 대기점은 직접 이동할 수 없습니다. 최종 판 전체에서 주간 한도, 전달 약속, 제출일, 의존관계 순환을 검사하며 위반이 하나라도 남으면 제안을 거부합니다. PM 권한으로 이 검사를 우회하는 옵션은 없습니다. 카드 한도 초과는 사람 동의로 해결하지만 일정 위반은 동의만으로 허용하지 않습니다. 중단된 작업의 남은 작업량 추정, 자동 다자 계획 탐색, 임의의 업무 의존관계 재작성은 지원하지 않습니다.

## 어떻게 동작하나

### 누가 무엇을 정하는가

| 주체 | 하는 일 | 코드 |
|---|---|---|
| ⬢ 프록시 (사람마다 하나) | 기록을 읽고 견적 고치기, 떼어 낼 조각 정하기, 요청에 수락 / 거절 / 조건부 / 본인 확인 필요로 답하기 | `app/llm.py` |
| ⚙ Hive (코드, LLM 없음) | 일정 다시 계산, 늦어질 Handoff 찾기, 프록시 답이 규칙 안인지 검사, 라운드 진행, 받을 사람 고르기, PM 선택지의 결과 미리 계산 | `app/hive.py`, `app/workflow.py` |
| ○ 사람 | 위임 카드로 한도를 정함. 한도를 넘는 일, 자기 일을 넘기는 것, 늦춰 받는 것만 확인 또는 거절 | `PUT /people/{id}/card`, `POST /confirmations/{id}` |
| PM | 선택지 허락, 이유를 적고 거절, 허락 없이 약속 늦추기, 규칙 바꾸기 | `POST /asks/{id}/grant`, `/reject`, `POST /handoffs/{id}/reagree` |

### 협상 한 건이 지나가는 단계

```
기본 경로            ingest -> help -> bids <-> tally -> propose -> confirm -> commit -> finish
한도를 넘으면        tally -> person (본인 확인) -> propose
받을 사람이 없으면   tally -> ask (PM 대기)
  PM 이 허락하면     granted -> bids (라운드 새로) 또는 cutconfirm -> finish
  PM 이 거절하면     bids (거절된 선택지를 빼고 라운드 새로)
  PM 이 약속을 늦추면 그 협상은 끝나고 받는 사람의 확인만 남음
```

사람이나 PM 을 기다릴 때는 `run.status` 가 `waiting_confirm` / `waiting_pm` 이 되고 멈춥니다. 답이 오면 같은 run 이 멈춘 단계부터 다시 돕니다. 진행 상태가 DB 에 있어서 서버를 껐다 켜도 이어집니다.

### 핵심 개념

**위임 카드.** 사람마다 프록시에게 맡긴 한도입니다.

| 칸 | 뜻 |
|---|---|
| `auto_days` | 이 일수까지는 프록시가 알아서 수락. 넘으면 본인에게 물음 |
| `refuse_tags` | 받지 않는 일의 종류 |
| `gives_help` | 30분 도움 요청을 프록시가 받아도 되는가 |
| `wait_days` | 받기로 한 것이 이만큼 늦어져도 알아서 수락 |
| `model` | 이 프록시만 쓸 LLM (Live 모드) |
| `note` | 자연어 사정·선호·휴가 문구. 해석 초안은 사람 검토 필요 |
| `policy` | 사람이 확인한 바쁨·휴가·명시적 주간 한도 |

한도를 넘는지는 코드가 검사합니다. 프록시가 뭐라고 답했든 넘으면 본인에게 묻습니다.

**프록시의 답.** 프록시는 자기 사람의 카드 · 일정 · 기록만 보고 고릅니다.

| 답 | 뜻 |
|---|---|
| `ACCEPT` | 한도 안이고 일정에 들어감. 프록시가 알아서 맡음 |
| `NEEDS_INPUT` | 들어가지만 한도를 넘음. 뽑히면 본인에게 먼저 물음 |
| `COUNTER` + `help` | 누가 30분 봐 주면 가능. 다음 라운드에 그 사람의 프록시에게 물음 |
| `COUNTER` + `defer` | 내 일 하나를 2주차로 미루면 가능. 미루기는 PM 전용이라 PM 의 선택지가 됨 |
| `REJECT` | 맡을 수 없음. 이유가 PM 에게 그대로 보임 |

Hive 는 `hive.check_reply()` 로 답이 규칙 안인지만 보고, 어긋나면 이유(`OVERLOAD`, `BAD_CONDITION`)를 붙여 한 번 돌려보냅니다. 반려는 라운드를 쓰지 않습니다.

**라운드.** `bids` 한 번이 한 라운드입니다. 1라운드는 같은 역할의 프록시들에게 조각을 맡아 달라고 묻고(조각에 `role` 이 적혀 있으면 그 역할에게, 예: 데모 2 의 DB 조각은 화면 쪽에게), 다음 라운드는 조건을 확인합니다. 규칙 `rounds`(기본 3) 안에 못 풀면 남은 항목과 함께 PM 에게 갑니다.

**받는 쪽의 참여.** 어떤 답대로 가면 뒤 약속이 늦어질 때(`hive.preview_offer()` 로 미리 봄), 담당 프록시가 받는 쪽 프록시에게 "늦게 받아도 돼요?"를 묻습니다. 받는 쪽 프록시는 자기 사람의 일이 제출일 뒤로 밀리는지, 넘길 약속이 깨지는지를 보고 답합니다.

**PM 의 답 세 가지.** PM 확인이 오면:

1. **허락.** 선택지 하나를 고릅니다. 각 선택지에는 고르면 누가 언제까지 맡고 무엇이 밀리는지가 미리 계산되어 붙습니다.
2. **거절.** 선택지를 체크하고 이유를 적습니다. 이유가 없으면 거절되지 않습니다. 거절한 선택지는 다시 나오지 않고, 프록시들이 다시 협상합니다. Live 모드에서는 이유가 LLM 에게 전달되고, Mock 프록시는 이유 문장을 읽지 못하고 거절된 조건을 피하기만 합니다.
3. **약속 늦추기.** 허락 없이 그 Handoff 의 약속을 예상 시각으로 다시 정합니다. 받는 사람이 확인해야 굳습니다.

**프록시의 기억과 모델.** Live 모드에서 각 프록시는 그 협상에서 자기가 주고받은 말만 다시 받아 보고 답합니다. 다른 프록시끼리의 말은 보지 못합니다.

```
seed.py         DB 를 비우고 지금 데모의 시드로 다시 채움
eval/           평가 결과 (보고서 .md, 표 .csv)
docs/           Report.pdf · AGENT_CALL_FLOW.md · DEMOS.md (문서 세 개)
assets/docs/    호출 흐름 Figure의 PNG · SVG
scripts/        Figure 및 데모 문서 생성 스크립트
tests/
```

새 데모를 만들려면 `seed/demo3/` 에 세 파일을 넣으면 됩니다. `PLANBEE_DEMO=demo3` 으로 켜거나 화면의 데모 고르기에 나타납니다.

## 화면

`web/index.html` 하나입니다. 서버가 같은 주소에서 내보내므로 저장하고 브라우저를 새로 고치면 바로 보입니다.

- 화면은 `GET /state` 로 받은 값을 `adopt()` 로 `S` 에 얹어 그리고, 버튼은 `act()` 로 서버를 부릅니다.
- 모양(CSS, `paint…` 함수)은 프로토타입 그대로라 디자인을 바꿀 때 서버는 건드릴 필요가 없습니다.
- 입력 탭의 **직접 누르기**를 켜면 팀원 확인을 서버가 대신 누르지 않고 기다립니다.
- 입력 탭의 **위임 카드**에서 −½ / +½ 로 한도를 바꿀 수 있습니다.
- 일이 길어져 2주차 화요일을 넘기면 판의 날짜 칸이 늘어나고 가로로 스크롤됩니다.

## API

`GET /state` 하나가 화면을 그리는 데 필요한 전부를 돌려줍니다. 상태를 바꾸는 요청도 모두 바뀐 `/state` 를 돌려줍니다.

| 화면 | 동작 | API |
|---|---|---|
| 공통 | 처음 그리기, 다시 그리기 | `GET /state` |
| 공통 | 시연: 다음 기록 받기 | `POST /demo/advance` `{auto_confirm}` |
| 공통 | 데모 바꾸기 | `GET /demos`, `POST /demo/select` `{demo}` |
| 공통 | 되돌리기 / 처음부터 | `POST /undo` / `POST /reset` |
| 입력 | 들어온 기록 | `GET /records`, `POST /records` |
| 입력 | 규칙, 받을 사람 기준, 라운드 수 | `GET /rules`, `PUT /rules/pref`, `PUT /rules/rounds` `{max}` |
| 입력 | 위임 카드 | `GET /cards`, `PUT /people/{id}/card` |
| 입력 | 팀원 확인 | `GET /confirmations`, `POST /confirmations/{id}` `{ok}` |
| 판 | 막대 · 화살표 · 남은 여유 | `GET /board` |
| 판 | 오간 말 | `GET /log?hid=` |
| 판 | 협상 과정 (제안 · 답 · 라운드별 오간 말) | `GET /negotiations`, `GET /negotiations/{id}` |
| 판 | 막대 자세히 | `GET /tasks/{id}` |
| 판 | 일 옮기기 (화면에서는 꺼져 있음) | `GET /tasks/{id}/bids`, `POST /tasks/{id}/move` `{dest}` |
| Handoffs | 목록 · 걸러 보기 · 집계 | `GET /handoffs?filter=all|watch|live|done` |
| Handoffs | 자세히 | `GET /handoffs/{id}` |
| Handoffs | PM 확인: 허락 | `POST /asks/{id}/grant` `{key}` 또는 `{index}` |
| Handoffs | PM 확인: 이유를 적고 거절 | `POST /asks/{id}/reject` `{reason, keys}` |
| Handoffs | PM 확인: 약속 다시 정하기 | `POST /handoffs/{id}/reagree` |

`auto_confirm: true` 는 시연용으로 사람 확인을 서버가 대신 누릅니다. `false` 면 확인에서 멈추고 `pending_confirms` 에 쌓이며, 그동안 새 기록과 다른 PM 조작은 409 로 막힙니다.

## 알려진 한계

- 합의 실패는 모든 배분안을 탐색한 불가능 증명이 아닙니다. 라운드와 제안의 질에 따라 결과가 달라집니다.
- 업무 범위가 의미상 겹치지 않는지, 공유 상태를 안전하게 분리할 수 있는지는 LLM과 당사자의 검토가 필요합니다. 코드는 분량 합계·의존관계·날짜·용량을 검증합니다.
- Mock의 PM 피드백 처리는 대본과 금지된 조건 회피에 한정됩니다. Live는 공개 피드백과 자기 위임 설정을 보고 판단합니다.
- Live에서 실제 합의에 도달하는지는 모델·출력 형식·업무 맥락에 따라 달라집니다. 자동 수락이나 범위 삭제로 성공을 강제하지 않습니다.

## 프로토타입 대본과 다른 점 (데모 1)

- **확인하는 사람이 다릅니다.** 위임 카드 때문에 Ivy 는 한도(½일)를 넘어 본인이 확인하고, Sam 은 한도(1일) 안이라 프록시가 알아서 수락합니다.
- **Sam 의 답이 다릅니다.** 목요일에 "넘침" 대신 "버그 고치기를 미루면 가능"이라는 조건을 내고, 이것이 PM 의 선택지가 됩니다.
- **마감 밖 제안을 먼저 제외합니다.** Ben이 맡아 기존 약속이나 후속 제출일이 늦어지는 경로는 정상 복구안에서 제외합니다. 수신자의 늦춰 받기 권한으로 프로젝트 마감을 우회하지 않습니다.
- **PM 이 거절할 수 있습니다.** 프로토타입은 허락만 있습니다.
- **사람 확인을 실제로 기다립니다.** 거절도 받습니다.
- **남는 일 나누기는 확인 뒤에 반영됩니다.** `캐릭터 몸`, `상태 머신 연결` 은 가약속 때가 아니라 당사자 확인 뒤에 판에 나타납니다.
- **시각 표기는 시연용 시계입니다.** `수 09:10` … 은 메시지 하나에 1분씩 갑니다.

협상 호출량 제한: `PLANBEE_MAX_NEGOTIATION_CALLS=40 .venv/bin/python start.py --llm live`

기본 한도는 run의 discussion 전체 40회입니다. 라운드 수와 별도이며 전략 전환이나 마감 복구 후 공정성 협상에서도 예산을 공유합니다. Live 전송 재시도와 한 응답 안의 추가 모델 호출도 포함합니다. 견적·최초 help 등 discussion 외 호출은 제외합니다. 한도 도달 시 미합의 변경을 적용하지 않고 `max_llm_calls` 사유와 호출 사용량을 PM summary에 남깁니다. 설정 변경은 새 run부터 적용됩니다.

토론 agent 프롬프트는 [prompts/discussion/README.md](prompts/discussion/README.md)에 모았습니다. 수락·거절, 독립 분할, 재제안, 전략별 요구사항과 오류 복구 지시를 각 MD에서 수정할 수 있으며 실제 Live 호출이 이 파일들을 읽습니다.
