# 데모 시나리오와 실행 안내

모든 인물·업무량·위임 설정은 합성 시연 데이터입니다. 초기 보드·카드·Task 상세는 현재 시드에서 계산합니다.

## 시작과 브라우저 사용

```bash
.venv/bin/python start.py --llm live
# 재현 가능한 Mock 실행
.venv/bin/python start.py --llm mock
```

Live 실행은 `.env`에 `OPENROUTER_API_KEY`가 필요합니다. 브라우저 상단에서 데모를 고르고 시연 버튼을 순서대로 누릅니다. 데모 전환 시 초기 상태로 시작합니다. 실행 세부 설정은 [README](../README.md), 협상·제약 검증은 [에이전트 호출 흐름](AGENT_CALL_FLOW.md)을 참고하세요.

화면 상단의 01 입력·재견적 / 02 기한 회복 / 03 공정성 협상은 처리 단계입니다. 협상 라운드 수와 데모 시연 순서는 별도로 표시합니다. Run 파일도 처리 단계별 섹션으로 대화·Hive 검증·마일스톤을 기록합니다.

## 데모 1 · 게임 개발팀

### 질문과 설정

게임 프로토타입을 금요일에 제출하는 6인 팀입니다. 먼저 캐릭터 그림이 늦고, 다른 날에는 캐릭터 코드를 구현하는 일이 늦습니다. 두 경우 모두 독립 조각을 나눌 수 있는지 확인합니다. 그림→코드→테스트 Handoff가 있어 앞 작업의 지연은 뒤 일정에 전파됩니다.

모든 인물·작업량·경력·메신저 기록은 시연용 합성 자료입니다. 사람 확인은 시뮬레이터에서 자동 승인됩니다.

### 팀과 위임카드

| 사람 | 역할 | 카드 권한/메모 | 시나리오상 특징 |
|---|---|---|---|
| Mia | 그림 | 1일까지 자동 수락 | 원 담당자. 그림 경험 6건 |
| Ivy | 그림 | 0.5일까지 자동 수락 | 배경 경험은 많지만 캐릭터 그림 경험은 1건 |
| Leo | 개발 | 1일까지 자동 수락 | 캐릭터 코드 경험 4건 |
| Sam | 개발 | 1일까지 자동 수락 · “오전엔 리뷰 안 받음” | 버그 경험 9건, 이번 주 일정이 꽉 참 |
| Ben | 개발 | 1일까지 자동 수락 | 요청 코드 경험은 없고, Sam의 도움을 조건으로 제안 |
| Zoe | 테스트 | 0.5일까지 자동 수락 | 테스트 경험 12건, 후속 테스트 담당 |

카드 한도를 넘는 수락은 프록시가 확정하지 않고 당사자 확인으로 보냅니다. PM만 업무를 다음 주로 미루거나 제출 범위를 줄일 수 있습니다.

### 사건과 Mock 제안

1. 수요일 기록: Mia가 `무기_v3.psd`를 세 번째 다시 올리고 그림이 3일째 진행 중입니다. Mock은 캐릭터 그림 견적을 3일에서 4일로 올립니다. 담당 Proxy는 무기 그림 1일을 독립 조각으로 제안합니다. Ivy의 자동 한도(0.5일)를 넘으므로 Ivy와 Mia가 각각 확인합니다.
2. 목요일 기록: Leo가 상태 머신을 새로 만드는 커밋을 올렸습니다. 캐릭터 코드 견적을 1.5일에서 2.5일로 조정합니다. 움직임 코드 1일을 분리해 Sam·Ben에게 묻습니다. Sam은 버그 작업을 2주차로 미루면 가능, Ben은 Sam이 30분 도와주면 가능하다고 답합니다. 이 조건은 PM 권한이므로 PM 검토가 필요합니다.

최신 실행은 README의 Mock 시작 명령과 아래 초기 보드를 기준으로 재현합니다.

## 데모 3 · 위임카드 네 조건

### 고정 시나리오

개발자 Mia의 기능 구현이 3일에서 4일로 늘었습니다. 테스트를 맡은 Ara가 금요일 전에 기능 코드를 받아야 하므로, `독립 기능 코드` 1일을 같은 역할의 Jun 또는 Sol에게 요청합니다. Jun은 이미 4.5일, Sol은 2일의 개발 작업이 있어 Jun은 추가 수락이 불가능하고 Sol은 가능합니다. 원 요청자인 Mia도 넘기는 조각을 확인합니다.

모든 조건에서 팀, 작업, 사건, 역할, 시드, 사람 확인 자동 승인, 실제 Hive 일정 검사는 동일합니다. 실험에서만 후보 Proxy에게 주는 정보와 자동 수락 권한을 바꿉니다.

### 2×2 조건

| 조건 | 개인 여건 정보 | 자동 수락 권한 | 카드 설정 의미 |
|---|---|---|---|
| 1 · 카드 없음 | 없음 | 0일 | 제안은 공통 기준값, 실제 일정은 Hive가 걸러냄 |
| 2 · 여건만 | 있음 | 0일 | 자기 작업량·경험·미룰 업무를 보지만 사람 확인 필요 |
| 3 · 권한만 | 없음 | 1일 | 일정 정보가 제한된 상태에서 1일까지 제안 가능 |
| 4 · 둘 다 | 있음 | 1일 | 개인 여건을 보고 한도 안에서 자동 수락 가능 |

“객관적 여건 정보”는 Proxy가 자기 작업량·역량·미룰 수 있는 업무를 아는 것을 뜻합니다. “권한”은 자동으로 맡겠다고 확정할 수 있는 최대 일수입니다. 타인의 카드 원문은 각 Proxy에게 공개되지 않습니다.

### 실행 결과

| 조건 | 배정된 사람 | 확인 | Hive 반려 | PM 결정 | 제출일 초과 |
|---|---|---:|---:|---:|---:|
| 카드 없음 | Sol | 2 | 1 | 0 | 0 |
| 여건만 | Sol | 2 | 0 | 0 | 0 |
| 권한만 | Sol | 1 | 1 | 0 | 0 |
| 둘 다 | Sol | 1 | 0 | 0 | 0 |

이 작은 사례에서는 정보가 실제 일정에 맞는 후보 답을 만들어 엔진 반려가 줄었고, 자동 권한은 사람 확인을 한 번 줄였습니다. 네 조건 모두 같은 1일 요청을 Sol이 맡았으므로, 이 결과만으로 장기 성능이나 공정성 향상을 주장하지 않습니다.

## 데모 4 추가 기능 · 원자적 묶음 이동

### 목적

서로 연결된 여러 작업의 교환·재배치를 한꺼번에 검증하고 확정하는 API 예제입니다. 일반 협상 LangGraph 흐름에 포함된 LLM 데모는 아닙니다. `app/bundles.py`가 작업 목록을 받아 전체 일정·선후 관계·용량을 미리 계산하고, 관련 당사자 전원의 확인 후 한 번에 반영합니다. 한 사람이 거절하면 부분 적용을 남기지 않고 전체를 취소합니다.

### 시나리오 공통 설정

Mia와 Jun은 개발 역할, Sol도 개발 역할이며 Ara는 테스트입니다. 세 개발자는 개발 경험 3으로 설정되고, 묶음 예제의 카드 자동 한도는 각 2일입니다. 모든 작업·사람·일정은 메모리 DB에서 만든 합성 자료입니다.

### 네 실행 사례

| 사례 | 제안 | 예상 확인자 | 결과 |
|---|---|---:|---|
| swap | Mia의 `x`와 Jun의 `y`를 서로 교환 | 2 | committed |
| split | Mia의 `x`를 Jun·Sol에게 각 0.5일 분배 | 1 | committed |
| chain | `x`, `y`, `z`를 Mia→Jun→Sol→Mia로 순환 이동 | 3 | committed |
| reject | 맞교환 중 둘째 당사자가 거절 | 2 | cancelled; 일부 이동 없음 |

네 사례 모두 이후 실제 일정·규칙 검사가 통과했습니다. `reject`는 실패한 제안이 규칙에 맞게 취소된 경우라 실행 자체의 실패가 아닙니다.

PLANBEE_LLM=mock .venv/bin/python run_bundle_demo.py --case all

각 실행 전후 상태는 `eval/bundles/{swap,split,chain,reject}.json`, 요약은 `eval/bundles/RESULTS.md`에 저장됩니다.

## 데모 4 · 업무 맥락, 모호한 위임카드, 부하 균형

### 업무 맥락

Plan Bee 프로젝트의 재개 로직이 지연되어, 담당 Proxy가 전체 일을 무작정 쪼개는 대신 목적·파일·산출물·분리 경계·완료 조건을 보고 판단합니다.

| Task | 목적/산출물 | 분리 경계 | 제안/기대 처리 |
|---|---|---|---|
| 협상 재개와 증거 로그 | 재개 코어와 읽기 전용 증거 조회 | 읽기 전용 조회는 독립 가능. 상태 전이·동의 트랜잭션은 나누지 않음 | `읽기 전용 증거 로그 API` 1일 분리 |
| 일회성 승인과 서명 키 교체 | 키 교체와 이중 확정 방지 | 공유 키·감사 기록이 한 트랜잭션에 있어야 함 | 분리 불가로 표시 |
| 사용자 인터뷰 동의서 | 확인된 동의서 | 개인정보 원문은 나누지 않음 | 분리 불가 |
| 리허설 배포 점검 | 정상 URL | 체크리스트 기반 검사는 독립 가능 | 후보 작업으로는 가능하나 현재 이슈 조각은 아님 |

### 결과: 후보 선택 기준만 변경

사건·카드·역량·업무량은 고정하고 선택 기준만 `fast`와 `fair`로 바꿨습니다.

| 기준 | 최종 후보 | 본인 확인 | 과거+현재 업무량 분산(분산값) | 범위 | 기한 초과 |
|---|---|---:|---:|---:|---:|
| 빠른 종료 (fast) | 주호 | 2 | 10.796875 | 9.0 | 0 |
| 누적 부담 균형 (fair) | 정민 | 1 | 6.125 | 6.5 | 0 |

정민은 휴가 시작 전 독립 API를 맡을 수 있으므로 두 후보 모두 마감은 지켰습니다. 공정성 휴리스틱이 이 시나리오에서 더 낮은 분산 후보를 골랐다는 관찰이며, 전역 최적성이나 실제 팀 효과를 뜻하지 않습니다.

### 마감 위험이 없을 때의 공정성 경로

별도 실행에서는 같은 issue를 유지하고 증거 API Handoff의 약속만 금요일 저녁(4.5일)으로 늦춰, 견적 수정 뒤에도 전달 일정이 위험하지 않게 했습니다. 과거 부담+현재 작업량의 범위는 기본 기준(3일)을 넘고, 부담이 큰 담당자와 같은 역할의 낮은 부담 후보 사이도 2일 이상이어서 `fairness_gate`가 분담 검토를 시작합니다. LLM은 `읽기 전용 증거 로그 API` 1일을 분리하고, 후보 Proxy가 답한 뒤 Hive는 마감 위험을 만들지 않는 안 가운데 부담 분산을 가장 낮추는 수락안을 고릅니다.

이 실행에서는 정민이 1.5일을 맡았고, 업무 소유자 여경이 확인했습니다. 마감 위험은 0건이며, 분산은 8.80에서 6.12로 낮아졌습니다. **기한이 지켜진다고 바로 종료하지 않고, 불균형이 기준을 넘으면 위임·카드·동의 단계를 거치는 경로**를 확인한 Mock 결과입니다.

## 데모 6 · 10인 교차 리전과 미합의·원자적 복구

### 시나리오 유형과 관찰 목표

10명이 24개 작업과 4개 milestone을 다룹니다. 백엔드·QA·운영의 서로 다른
업무 줄과 원장→QA→릴리스의 의존관계, 두 리전의 배포·롤백 준비가 연결됩니다.
첫 협상은 기한을 넘는 대안을 차단하고 최대 라운드에서 멈추는 실패 경로입니다.
이후 원장 2조각 분할과 운영 작업 맞교환을 하나의 묶음으로 재배치합니다.

### 브라우저 실행과 기대 흐름

1. `demo6_cross_region`을 고르고 첫 단계를 실행합니다. 준의 거절 후 카이에게
   6일짜리 검증을 요청하는 대안은 Hive가 데드라인 위반으로 차단합니다.
   안전한 수정안을 냈더라도 최대 3라운드 안에 전원 동의를 받지 못하면
   `max_rounds`로 끝나며 원래 작업 배정을 유지합니다.
2. 두 번째 단계는 원장 1일씩을 준·카이에게 분리하고 노엘·올린의 운영 작업을
   맞교환하는 **4건의 원자적 묶음**입니다. 전원 동의 전에는 어느 작업도 적용하지 않습니다.
   ‘직접 누르기’ 상태에서 한 명을 거절시키면 전체 취소도 확인할 수 있습니다.
3. 마지막 정합성 검사 입력 기록을 처리하고 금요일까지의 전체 기한을 재검증합니다.

묶음은 LLM이 자동 생성하는 협상안이 아니라, 데모에서 명시한 대안에 당사자 동의를
받는 기존 묶음 API입니다. 첫 단계의 다자간 협상과 구분해서 관찰하세요.

## T1. Simple Rescheduling

: 다른 담당자와 협상할 필요가 없는 일정 변경.

[원본 일정 보드](/demos/m4_t1_rescheduling/board)

1. 변경 요청
    
    Dev → Polish 작업을 하루 뒤로 이동하고 싶습니다. Bug Fix와 Core X 일정은 그대로 유지하고 싶습니다.
    
2. 협의 참여 에이전트
    
    없음. Dev Agent 단독 처리.
    
3. 협상에 관여하는 담당자별 제약 및 위임 규칙
    
    Dev : Polish는 P3. 11/25까지 완료하면 되며 본인 작업을 1영업일 이내 이동 가능. 11/23 작업 총량은 8h 이하.
    
    QA : Final Test는 Core X와 Bug Fix 완료 후 진행. Polish는 필수 테스트 선행 작업이 아님.
    
4. 기대하는 협상안(예시)
    
    Polish를 11/23 이동. 협상이 필요없다는 것을 AI 자동 확인. contraint 확인 후 단순 일정 조정.
    
5. AI prompt evaluation
- 불필요한 협상 방지 : 다른 작업에 영향이 없음을 확인하고 GD, Art, QA에게 연락하지 않았는가.
- 위임 규칙 준수 : Dev의 1 영업일 이동 권한을 정확히 적용하는가
- 일정 검증 : 11/23의 가용 8h 안에 polish 6h가 들어가는지 확인하는가
- 정확한 변경 : polish만 이동하고 Bug fix 및 QA 일정은 유지하는가

## T2. Task Reallocation

: 서로 다른 담당자 간 작업 재분배

[원본 일정 보드](/demos/m4_t2_reallocation/board)

1. 변경 요청
    
    Dev → UI Integration 작업에 예상보다 하루가 더 필요할 것 같습니다. Bug Fix는 예정대로 끝내야 합니다. 작업의 재분배를 요청합니다.
    
2. 협의 참여 에이전트
    
    Dev, Art
    
3. 협상에 관여하는 담당자별 제약 및 위임 규칙
    
    Dev : 11/23 가용 8h, 11/24 가용 8h. UI Integration 중 로직 연결 8h는 Dev 전담. Bug Fix 8h도 Dev 전담. UI Integration은 기존 8h에서 총 16h로 증가했으며, 로직 연결 8h와 에셋 연결 8h로 분리 가능.
    
    Art : 11/23 가용 8h, 기존 배정 없음. UI Integration의 에셋 연결 8h를 수행할 역량 있음. 신규 작업 인수는 Art 본인 Confirm 필요.
    
    QA : UI Integration 및 Bug Fix 완료 후 11/25~26에 Integration Test 16h. 작업 담당자가 바뀌어도 테스트 범위 축소 불가.
    
4. 기대하는 협상안(예시)
    
    Dev는 11/23 로직 연결 8h, 11/24 Bug Fix 8h. Art는 11/23 에셋 연결 8h를 인수. Art Confirm 이후 확정.
    
5. AI prompt Evaluation
- 적절한 협상 상대 탐색 : 작업을 인수할 수 있는 Art를 식별했는가
- 업무 역할 확인 : Dev 전답 작업과 Art에게 이전 가능한 작업을 구분하는가
- 권한 및 동의 : Art의 confirm을 제대로 전송하는가
- 일정 재계산 : Dev와 Art의 가용 시간, QA 선행 조건을 모두 만족하는가

### 과제 #3: 협력 — Agent Company

- **성적 반영 비율:** 전체 성적의 14%
- **제출 기한:** 12월 1일(화) 오후 11시 59분

#### 과제 개요

과제 2에서는 여러 에이전트가 서로 경쟁했습니다. 이번 Agent Company 과제의 핵심 질문은 **“여러 에이전트가 하나의 팀을 이루어 협력하게 하려면 어떻게 해야 하는가?”**입니다.

이전 과제와 마찬가지로, 자신이 작성한 `agent.md`를 사용하는 에이전트와 다른 에이전트 3개가 함께 4인 팀을 이루어 글쓰기 작업을 수행합니다. 글쓰기 결과물의 점수, 자신에게 배정된 평가 기준의 점수, 다른 팀원 에이전트가 부여한 동료 평가 점수를 바탕으로 `agent.md`를 개선하고, 개선 과정에서 발견하고 배운 내용을 보고서로 제출해야 합니다.

#### 작업 설명

팀은 WritingBench(NeurIPS 2025)의 작업을 수행합니다. 이 중 9개 작업이 선정되어 있습니다. 자신의 에이전트는 다음 순서로 참여합니다.

1. 먼저 운영진이 제공하는 기본 에이전트들과 팀을 이루어 9개 작업을 수행합니다.
2. 일정 시간이 지난 뒤 팀을 바꾸어, 나머지 학생 27명의 에이전트들과 9라운드를 수행합니다.

WritingBench의 각 질의에는 체크리스트 항목, 즉 **평가 기준 5개**가 있습니다. 팀의 에이전트 4개에는 각각 이 중 하나의 기준이 무작위로 배정됩니다. 각 에이전트는 최종 결과물이 자신에게 배정된 기준에서 높은 점수를 받도록 노력해야 합니다.

모두가 우호적이면 좋겠지만, 실제 회사에는 여러 이유로 자신의 성과 경쟁 상대가 되는 사람이 대개 한 명 이상 있습니다. 이 과제에서는 그 상대를 **라이벌(rival)**이라고 부릅니다. 따라서 자신의 에이전트에는 다음 세 가지 목표가 있습니다.

1. 자신에게 배정된 평가 기준에서 좋은 점수를 받기
2. 팀 전체의 결과물도 좋은 점수를 받도록 기여하기
3. 에이전트 간 동료 평가에서 자신의 라이벌보다 높은 순위를 얻기

#### 한 번의 run 진행 순서

다음 구조는 Debate-to-write(COLING 2025)를 일부 수정한 것입니다.

| 단계 | 내용 |
|---|---|
| **Assign — 배정** | 각 에이전트에 평가 기준과 라이벌을 배정합니다. 라이벌 관계는 양방향이 아니라 사슬 형태로 이어집니다. |
| **Plan — 계획** | 에이전트들이 대화를 통해 질의에 대한 초기 계획을 작성합니다. 모든 에이전트가 `Ready` 상태에 동의해야 계획 단계가 끝납니다. |
| **Initial draft — 초안 작성** | 중립적인 LLM이 계획을 바탕으로 글의 초안을 작성합니다. |
| **Parallel comment — 병렬 의견 제시** | 각 에이전트가 초안에 의견을 남깁니다. 에이전트마다 최대 3개의 의견을 남길 수 있습니다. |
| **Discussion — 토론** | 에이전트들이 다른 에이전트의 의견에 댓글을 달아 동의하거나 반대할 수 있습니다. |
| **Final draft — 최종본 작성** | 중립적인 LLM이 피드백을 바탕으로 최종 글을 작성합니다. |
| **Judge — 평가** | WritingBench에서 제공하는 LLM-as-a-Judge 프롬프트로 최종 결과물을 평가합니다. 또한 에이전트들은 CATME 프레임워크를 바탕으로 서로를 동료 평가하며, 상대적인 순위를 매깁니다. |

에이전트의 성격은 **Plan, Parallel comment, Discussion** 단계에 직접 반영됩니다. 이 단계에서 나타나는 자신의 에이전트 행동과 Judge의 평가를 살펴보며 `agent.md`를 개선하세요.

##### Agent Company: 20점

동급생의 에이전트들과 9라운드를 진행한 뒤, 자신의 에이전트 점수를 평균하여 평가합니다.

| 평가 항목 | 배점 | 산정 방식 |
|---|---:|---|
| 배정된 평가 기준 점수 | 6점 | 자신에게 배정된 기준의 모든 점수 평균 |
| 다른 평가 기준 점수 | 4점 | 자신에게 배정되지 않은 다른 기준들의 점수 평균 |
| 동료 평가 순위 | 6점 | 평균 순위 `R`은 1~3입니다. 점수는 `9 - (3 × R)`입니다. |
| 라이벌 보너스 | 4점 | 동료 평가에서 라이벌보다 높은 순위이면 2점, 배정된 기준 점수에서 라이벌보다 높은 점수를 받으면 2점 |

##### 형식: 5점

다음 다섯 가지를 확인합니다.

1. 파일 형식과 파일명
2. ZIP 파일 크기가 50MB 미만인지
3. `agent.md` 버전을 최소 3개 제출했는지
4. AI 사용 공개가 있는지
5. 보고서 첫 페이지에 이름과 학번이 있는지

- 다섯 가지를 모두 만족하면 **5점**
- 하나를 빠뜨리면 **2.5점**
- 둘 이상을 빠뜨리면 **0점**
