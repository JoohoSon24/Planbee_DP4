# Live LLM: 채팅으로 이슈를 보내고 역할을 바꾸며 체험하기

**시나리오 선택 → 내 역할 선택 → 줄글 입력 → 보내기 → 토론 확인 → PM 선택 → 당사자 확인** 순서입니다.

채팅창은 여러 줄 입력을 지원합니다. **Enter는 줄바꿈**, **Ctrl / ⌘ + Enter는 보내기**입니다. 역할 안내와 시나리오 설명은 펼쳐서 확인하고, 진행 상태의 **바로 보기**로 PM 결정·본인 확인 위치로 이동할 수 있습니다.

예시 버튼을 누르는 것이 실행의 시작은 아닙니다. **입력창에 글을 쓰고 ‘보내기’를 눌렀을 때** 실제 Live LLM 호출이 시작됩니다.

## 1. API 키 설정 — 처음 한 번

프로젝트 루트 `/Users/sonjooho/Desktop/planbee-backend`의 `.env` 파일을 편집합니다. 기존 설정이 있다면 보존하고 아래 키를 설정하세요.

```dotenv
OPENROUTER_API_KEY=여기에_본인의_실제_API_키
```

`여기에_본인의_실제_API_키`는 설명용 문자열이므로 실제 키로 바꿔야 합니다. 키는 이 문서나 run 기록에 붙여넣지 않습니다.

모델을 직접 지정하려면 같은 파일에서 설정합니다. 이미 설정한 모델이 있다면 그대로 사용할 수 있습니다.

```dotenv
PLANBEE_MODEL=사용할_OpenRouter_모델_ID
PLANBEE_GENERATOR_MODEL=후보_생성에_사용할_OpenRouter_모델_ID
```

위 두 줄은 **선택 사항**이며 예시 문자열을 그대로 추가하면 안 됩니다. `PLANBEE_GENERATOR_MODEL`을 생략하면 기본 모델을 사용합니다. 개인 위임카드에 별도 모델이 설정되어 있으면 해당 개인 호출은 카드의 모델을 사용합니다.

`.env`를 바꾼 뒤에는 서버를 다시 시작해야 합니다. 터미널에 같은 이름의 환경변수가 이미 설정되어 있으면 그 값이 `.env`보다 우선합니다.

## 2. 기존 서버 종료 후 Live 서버 실행

기존 서버를 실행한 터미널에서 **Ctrl+C**로 종료합니다. 새 터미널에서 다음 두 줄을 실행하세요.

```bash
cd /Users/sonjooho/Desktop/planbee-backend
.venv/bin/python start.py --llm live --demo m4_t1_rescheduling
```

**`--llm live`를 반드시 붙입니다.** 생략하면 기본값이 Mock일 수 있습니다.

터미널에서 다음 표시를 확인합니다.

```text
Plan Bee 대시보드: http://127.0.0.1:8000
시작 데모: m4_t1_rescheduling | LLM: live
```

서버가 실행되는 동안 이 터미널은 열어 두세요. 브라우저가 자동으로 열리지 않으면 **http://127.0.0.1:8000**에 접속합니다. `front/Plan Bee Front.html` 파일을 직접 열면 안 됩니다.

화면 상단 배지가 **LIVE**인지 확인하세요. 더 확인하려면 브라우저에서 **http://127.0.0.1:8000/runtime**을 열어 `llm_mode`가 `live`인지 확인할 수 있습니다. 이 표시는 호출 모드이며, 실제 모델 호출 성공 여부는 요청 실행 후 대화와 종료 상태로 확인합니다.

> `.venv/bin/python`이 없거나 패키지가 설치되지 않은 경우에만 최초 설치:
>
> ```bash
> cd /Users/sonjooho/Desktop/planbee-backend
> python3.13 -m venv .venv
> .venv/bin/python -m pip install -r requirements.txt
> ```

## 3. 화면에서 내 역할부터 확인하기

상단 **내 역할** 선택 상자와 대화 패널의 **현재 내 역할** 표시를 확인합니다.

| 내 역할 | 내가 할 수 있는 일 |
|---|---|
| PM · 최종 결정자 | 팀의 이슈 요청, 후보 비교, 최종 후보 선택·반려·수정 요청, 실패 summary 확인 |
| Dev 본인 | Dev의 업무 이슈 입력, 자기 위임카드 확인, Dev 본인 동의·거절 |
| Art 본인 | Art의 업무 이슈 입력, 자기 위임카드 확인, Art 신규 업무 인수 동의·거절 |
| GD 본인 | 기획 담당 관점 확인, 자기 카드와 가능한 업무 확인, GD 본인 확인 요청 처리 |
| QA 본인 | QA 관점·카드 확인, QA 본인 확인 요청 처리 |

업무 선택란 없이 이슈를 보내면 LLM이 공개 Task 설명을 읽고 관련 업무를 찾습니다. 담당 업무가 없는 역할도 팀 이슈를 보고할 수 있습니다. 대상이 모호하면 질문하고 입력을 유지합니다. **내 위임카드 확인**을 펼치면 선택한 사람의 카드를 볼 수 있습니다. 자기 업무 줄은 보드에서 강조됩니다.

역할을 바꾸는 것은 브라우저에서 사람의 입장을 체험하는 기능입니다. 로그인 인증이 아니며, 역할 전환만으로 LLM을 호출하지 않습니다. 자동 토론에서는 각 LLM이 계속 자신의 신원과 카드로 판단합니다. 사람이 다른 사람의 수락을 대신 입력하려면 해당 사람 역할로 명시적으로 전환해야 합니다.

## 4. 처음에는 T2를 채팅으로 실행하기

1. **시나리오**에서 **T2 · Task Reallocation · 업무 재분배** 선택.
2. **내 역할**에서 **Dev · 개발 담당자** 선택. 패널에 **현재 내 역할: Dev 본인**이 표시되는지 확인.
3. 업무는 따로 선택하지 않습니다. 문장에 UI Integration에서 무엇이 바뀌었는지 적습니다.
4. 아래 문장을 하단 채팅 입력창에 그대로 붙여넣기.

```text
UI Integration 작업에 예상보다 하루가 더 필요합니다. 기존 8h에서 총 16h(2일)로 증가했습니다. 로직 연결 8h는 Dev 전담이고, 에셋 연결 8h는 Art에게 분담할 수 있습니다. Bug Fix는 예정대로 끝내야 합니다. 일정 안에 끝낼 수 있도록 작업 재분배를 논의해 주세요.
```

5. **보내기** 클릭. 이때 실제 Live 호출이 시작됩니다.
6. 후보 생성 → 카드 기반 토론이 자동 진행될 때까지 기다리기. 화면 상단의 단계·개인 평가 진행 수·호출 수가 바뀝니다.
7. **PM 최종 결정**이 표시되면 **내 역할 → PM**으로 전환하거나 **PM으로 전환해 최종 선택** 클릭.
8. 번호별 후보의 **보드에서 보기**로 비교하고, 필요하면 **변경 내용 · 일정 자세히**를 펼친 뒤 팀 추천 후보의 **이 안으로 결정** 클릭.
9. **Art 본인 확인**이 뜨면 **Art 본인으로 전환** 클릭 → **당사자로서 동의** 또는 **거절**. Dev 확인도 있으면 Dev로 전환해 처리.
10. 모두 동의하고 Hive 검증을 통과하면 변경된 보드와 적용 완료 문구 확인.

Art의 위임카드는 신규 인수에 본인 확인을 요구합니다. PM이 선택했다고 Art의 동의가 자동으로 처리되지는 않습니다. 후보가 하나라도 PM 선택이 필요합니다.

**예시 이슈 채우기** 버튼은 해당 시나리오의 문장을 입력창에 채우기만 합니다. 필요한 대로 고친 후 **보내기**를 눌러야 실행됩니다. 줄글만 입력하면 되고 JSON이나 Task ID를 직접 입력할 필요는 없습니다.

## 5. 시나리오별로 어떤 글을 입력할까?

각 시나리오를 새로 고른 뒤 아래 역할에서 문장을 붙여넣어 **보내기**를 누르세요. 결과는 Live 모델의 판단에 따라 달라집니다. 아래 내용은 정답을 강제로 지정하는 지시가 아니라 문제와 요청입니다.

### T1 · 일정 이동

- 시나리오: **T1 · Simple Rescheduling · 일정 이동**
- 내 역할: **Dev** / 자동 식별 대상: **Polish**

```text
Polish 작업을 하루 뒤인 11/23으로 이동하고 싶습니다. 소요량은 6h 그대로입니다. Bug Fix와 Core X 일정은 그대로 유지하고, 다른 사람에게 영향 없이 제 가용 시간 안에서 이동할 수 있는지 확인해 주세요.
```

확인할 점: Polish만 바뀌는지, 1영업일 이동 권한과 가용 시간을 지키는지. 현재 V2 공통 정책상 최종 적용에는 PM 선택이 필요합니다.

### T2 · 업무 재분배

- 시나리오: **T2 · Task Reallocation · 업무 재분배**
- 내 역할: **Dev** / 자동 식별 대상: **UI Integration**

```text
UI Integration 작업에 예상보다 하루가 더 필요합니다. 기존 8h에서 총 16h(2일)로 증가했습니다. 로직 연결 8h는 Dev 전담이고, 에셋 연결 8h는 Art에게 분담할 수 있습니다. Bug Fix는 예정대로 끝내야 합니다. 일정 안에 끝낼 수 있도록 작업 재분배를 논의해 주세요.
```

확인할 점: Dev 전담 로직과 Art에게 맡길 수 있는 에셋을 구분하는지, Art 본인 Confirm을 받는지, QA 일정과 테스트 범위를 유지하는지.

### T3 · 범위 축소

- 시나리오: **T3 · Scope Reduction · 범위 축소**
- 내 역할: **Dev** / 자동 식별 대상: **Advanced Effects**

```text
Advanced Effects 구현이 기존 16h에서 총 32h(4일)가 필요할 것으로 보입니다. Core Integration 8h도 다음 주에 마쳐야 해서 지금 계획으로는 Alpha 마감을 맞추기 어렵습니다. 저는 기능 우선순위를 모르니 GD와 범위 조정이 가능한지 논의하고, 필요한 승인을 구해 주세요.
```

확인할 점: GD의 우선순위 판단, 필수 Core 유지, 선택 기능과 잔여 FX의 Beta 이관 제안, PM 명시적 승인. Beta 이관 연산자를 추가했으며 GD의 동의와 PM 선택을 따로 받습니다. 실제 결과와 현재 지원 범위는 화면 설명·run 기록에서 확인하세요.

### T4 · 복합 협상

- 시나리오: **T4 · Composite Negotiation · 복합 협상**
- 내 역할: **Art** / 자동 식별 대상: **Character Animation**

```text
Character Animation에 하루가 더 필요해서 기존 24h에서 총 32h(4일)가 됩니다. 추가 8h는 11/20에 수행하므로 FX Assets 잔여 4h는 11/23 오전에 진행해 12:00에 전달할 수 있습니다. 임시 에셋은 11/20에 제공 가능합니다. Dev와 QA의 후속 일정에 영향이 있을 것 같으니 함께 조정해 주세요.
```

확인할 점: 임시 에셋 작업과 최종 교체의 분리, Critical Fix 재배치, Retest 생략에 대한 QA 본인 Confirm, Final QA 16h 유지. 단계별 작업 분해와 조건부 입력 연결, 선택 Retest 생략 연산자를 추가했습니다. 월요일에 임시 Integration과 최종 교체를 모두 끝내 Retest를 유지하는 안도 가능하므로, 생략만 정답으로 강제하지 않습니다. 현재 공통 V2에서는 적용에 PM 최종 선택도 필요합니다.

### T5 · 해결 불가능 충돌

- 시나리오: **T5 · Infeasible Conflict · 해결 불가능 충돌**
- 내 역할: **Dev** / 자동 식별 대상: **Critical Fix 추가 수정**

```text
Critical Fix에서 추가 결함이 발견돼 잔여 수정 16h(2일)가 필요합니다. 저는 11/26과 11/27에 각각 8h만 작업할 수 있고, 이 수정은 나누거나 다른 사람에게 넘기거나 범위를 줄일 수 없습니다. QA와 완료 후 검증 일정을 확인해서 11/27 릴리스가 가능한지 판단하고, 불가능하면 PM에게 보류 검토를 요청해 주세요.
```

확인할 점: 수정 전 QA 시작이나 테스트 축소를 제안하지 않는지, 필요한 QA 2영업일과 마감 충돌을 설명하는지, PM에게 현재 상황을 전달하는지. 초기 보드에는 새로 발견된 추가 수정 16h가 이미 표시되어 있습니다.

## 6. 진행 중 어떤 버튼을 누를까?

| 상태 | 할 일 |
|---|---|
| 02 후보 생성 / 03 카드 평가·토론 | 기다리기. 기본 자동 진행 |
| 현재 단계 뒤 잠깐 멈추고 싶음 | **다음 단계에서 일시정지**. 진행 중인 호출을 즉시 취소하지는 않음 |
| 새로고침·일시정지 후 `running` | **계속 진행** |
| PM 최종 결정 | **PM 역할**에서 후보 확인 → **이 계획으로 최종 결정** |
| 본인 확인 대기 | 표시된 **해당 사람 역할**로 전환 → 동의/거절 |
| 마음에 드는 후보 없음 | **PM 역할**에서 **모두 반려** 또는 **수정 요청**, 이유 입력 |
| 수정 요청 후 `running` | **계속 진행**. 기존 run의 호출 한도를 함께 사용 |
| PM 상황 전달 | **PM 역할**에서 **현재 상황 summary 보기** → **상황 확인 · 현재 배분 유지** |

PM 상황 전달은 마감 충족이나 문제 해결을 뜻하지 않습니다. 미합의 변경은 적용하지 않으며, 확인된 업무량 증가 때문에 보드에 마감 위험이 남을 수 있습니다. 후보 없음은 제한된 탐색의 결과일 수 있으며 모든 방법의 수학적 불가능성을 증명한 것은 아닙니다.

## 7. 재실행과 기록

- 다른 시나리오: 상단 **시나리오** 선택 → **내 역할** 선택 → 줄글 입력 → **보내기**.
- 같은 시나리오 재실행: **초기화** → 확인창 승인 → 새 글 입력 → **보내기**.
- 역할 전환은 run을 초기화하지 않습니다. 시나리오 전환과 초기화는 현재 보드·run을 초기 상태로 바꾸므로 결과를 먼저 확인하세요.
- **사람 순위 비교평가**는 별도 실험입니다. 협상 실행의 필수 절차는 아닙니다.
- 종료: 서버 터미널에서 **Ctrl+C**.

기본 Live 기록: `/Users/sonjooho/Desktop/planbee-backend/runs/v2/live/`

날짜·시간 MD에 순서대로 대화, Hive 검증, 후보, milestone, PM 선택과 종료 사유를 기록합니다. 진행 중에도 갱신됩니다. `PLANBEE_RUNS_DIR`을 지정했다면 그 경로가 우선합니다.

기본 run 한도는 전체 LLM 호출 120회, 처리 시간 600초입니다. Live에는 API 비용이 발생합니다.

## T4 자동 동의 데모

T4 화면은 공개 토론 1라운드 뒤 개인 동의를 LLM에 다시 묻지 않고 알고리즘으로 자동 수락합니다. 검증 후보에서 고정 seed로 최대 3개를 추천하며 **PM만 최종 선택**합니다. 자동 수락은 실제 카드 기반 합의가 아니며 run에 `demo_algorithm`으로 표시됩니다. PM 선택 전에는 미적용이고 선택 후 Hive 최신 제약 검증은 유지합니다. 다른 시나리오에는 이 데모 옵션을 허용하지 않습니다.

Live 처리 중에도 상단 내 역할을 바꿀 수 있습니다. 역할 전환은 화면만 바꾸며 새로운 LLM 호출이나 진행 중인 요청 취소를 발생시키지 않습니다.

## EN 대화 번역

**EN**에서는 이슈 본문·공개 발언·동의/거절 사유·추가 질문을 영어로 번역해 보여 줍니다. **한국어**로 전환하면 원문으로 돌아가며 DB와 run 기록은 바꾸지 않습니다. 번역 중에는 `Translating…`, 실패하면 `Retry translation`을 표시합니다. 같은 문장은 캐시로 재사용합니다. 번역은 Live 모델의 별도 표시용 호출이며 **사용량**에 포함됩니다. 협상 호출 예산과 분리하며 서버 실행 동안 run별 최대 32배치입니다. Mock 모드에서는 유료 번역을 호출하지 않습니다. 백엔드 변경 후 서버 재시작과 브라우저 새로고침이 필요합니다.

- T5 실패 전달에서는 PM이 **확인 · 현재 배분 유지**를 누르면 완료됩니다. 같은 요청이 재전송되어도 중복 확인 오류 없이 같은 완료 결과를 반환합니다.


## T6 후보 탐색 개선 검증

Q2 이관 후보는 Ben 단순 인수뿐 아니라 **Sam 스모크 인수 + S3 전체 금요일 이동**을 함께 탐색합니다. 시작 시각을 남은 주간 전체에서 확인하며 원래 업무량·Zoe 서명·QA→빌드 순서는 유지합니다. 최종 추천은 동의 조건을 충족하는 수신자별 대안을 우선 비교할 수 있게 구성하고 PM이 선택합니다. 후보 개수만 채우기 위해 검증 실패안을 넣지 않습니다.

기본값: 원시 후보 2,000개, 보존 후보 60개, 토론 shortlist 12개, 최대 6라운드·240호출·처리시간 1,200초. 새 쟁점이 없는 두 라운드 후에는 최종 평가로 넘어갑니다. T4 화면 데모의 1라운드 자동 동의 예외는 유지합니다. 탐색 기록의 `search_stop=raw_limit`은 탐색 한도이며 불가능 증명이 아닙니다.

```bash
# 실제 운영 DB와 분리해 세 seed로 반복 검증
.venv/bin/python scripts/verify_t6_search.py --repeats 3
# 실제 설정 모델, 유료 호출. PM 선택/개인 승인 없이 추천 도달까지만
.venv/bin/python scripts/verify_t6_search.py --live --repeats 1
```

추가 사례 원문 S01~S17은 시나리오 설명에 보존했습니다. 이 표의 모든 자연어 목표·가용시간 변경을 자동으로 해석하는 전용 흐름이 구현된 것은 아닙니다. 특히 S17 금요일 정오 마감은 원문도 현 제약상 불가능으로 규정합니다. 필수 서명·QA·빌드 시간을 줄인 허위 후보로 통과시키지 않습니다. S12 신규 상점 업무, S16 두 보고를 합치는 전용 흐름, T3 사전 본인 승인 및 적용분만 Undo는 별도 구현이 필요합니다.


검증한 사례: S01의 Ben·Sam 대안(3개 seed), Ben도 부재인 Sam 단독 복구, S03 G1 이동, S05 B2 이동, S06 Q1 두 시각, S07 A2 금요일 이동/이관, S08 S3 금요일 이동, S17 마감 단축 차단입니다. 일정 이동 사례는 보고 사실을 Task의 명시적 변경 계약으로 구성해 후보 엔진을 검증했습니다. 임의의 자연어가 이 계약 전체를 자동 생성한다고 주장하지 않습니다. 프롬프트 변경 전 파일은 `prompts/past_versions/2026-11-24_search_expansion/`에 보존합니다. 반복 결과의 공개 통계는 `eval/t6_search/`, 대화 원문은 `runs/v2/mock/`·`runs/v2/live/`에 기록합니다.


2026-11-24 실제 Live 검증 1회: 원시 112개 검사 → Hive 검증 후보 11개 → 공개 토론 3라운드 → PM 추천 2개, 모델 호출 40회. 이후 새로운 실질 발언이 없어 안정 종료했으며 최대 6라운드를 억지로 채우지 않았습니다. PM 선택·본인 확인은 자동 처리하지 않았습니다. 이는 한 모델·한 시나리오의 재현 결과이며 모든 Live 실행의 성공 보장은 아닙니다. 상세 공개 통계는 `eval/t6_search/`의 `*_live.json`에 있습니다.


## EN 화면과 팀원 자동 확인

EN에서는 보드·후보·업무 팝업·시나리오 설명·독립 평가 화면의 동적 문구도 영어로 표시합니다. 번역 중/실패 안내도 영어이며 실패 시 **Retry English**로 재시도할 수 있습니다. Tab으로 삽입하는 예시는 영어로 번역한 뒤 입력합니다. 직접 작성한 입력 내용과 원본 카드·협상 기록은 바꾸지 않습니다. 영어 표시는 설정된 Live 모델의 별도 번역 호출 비용이 발생하며 캐시를 재사용합니다. 원본 일정 이미지는 한국어 보기에서 확인하고 EN에서는 텍스트 일정 보드를 사용합니다.

서비스 실행 기본값 `PLANBEE_AUTO_CONFIRM=1`에서는 T6의 Ben·Zoe 등 팀원 본인 확인도 **PM 선택 후 자동 승인**합니다. 이는 시연용 자동 확인이며 실제 사람이 승인했다고 기록하지 않습니다. REJECT는 자동 수락하지 않습니다. 직접 확인을 체험하려면 실행 환경에서 `PLANBEE_AUTO_CONFIRM=0`으로 지정합니다. 이 설정은 위의 이전 직접 확인 안내보다 우선합니다.


T6 시연 기본값은 `PLANBEE_T6_FORCE_AGREE=1`입니다. 모든 역할의 후보 평가는 무조건 동의로 처리하고, 공개 토론 후 검증 후보 최대 3개를 PM에게 올립니다. 이는 실제 카드 합의 실험이 아니며 `demo_algorithm`으로 기록합니다. 역할의 거절 때문에 `no_consented_candidate`로 끝나지 않지만 Hive 하드 제약 위반 후보를 통과시키지는 않습니다. 연구용 카드 판단을 복원하려면 `PLANBEE_T6_FORCE_AGREE=0`을 지정합니다.

턴이나 협상 완료 후 날짜는 **자동으로 넘어가지 않습니다**. `Next day / Previous day`를 직접 눌러 시연 시간을 이동합니다.


## T6 날짜별 연속 협상

T6는 현재 보드를 유지하면서 여러 차례 이슈를 처리합니다. 채팅 위의 **오늘 입력 가능한 이슈**를 펼치거나 빈 입력창에서 Tab을 누르세요. 예시 선택은 입력만 채우며 보내기 전에는 LLM을 호출하지 않습니다.

- 화요일 오후(D1.5): Zoe가 목요일 스모크 부재를 사전 보고하고 분담 계획을 PM이 선택합니다.
- 수요일 오후(D2.5): Mia의 A2 이펙트를 금요일로 이동합니다. B2 메뉴 이동도 현재 QA 분담과 충돌하지 않는 경우 선택할 수 있습니다.
- 목요일 오후(D3.5): 앞선 배분과 일정 변경을 유지하면서 G3의 QA 이후 인계를 재점검합니다.
- 금요일 오후(D4.5): 실제 완료 처리된 QA·서명을 기준으로 마지막 빌드 계획을 확인합니다.

각 협상을 끝낸 뒤 **Next day**로 직접 이동합니다. 이전 합의는 다음 run의 출발 보드가 되며, 이미 완료된 업무나 보고 시각이 지난 예시는 비활성화됩니다. 이전 협상 기록은 같은 영역에서 펼쳐 볼 수 있습니다. 메뉴 이동이 Ben의 스모크와 겹치는 등 새 충돌이 있으면 가능한 예시인 것처럼 노출하지 않습니다. 위 날짜별 이슈는 `seed/m4_t6_game_demo/timeline.yaml`에서 편집합니다. 이 목록이 원문 S01~S17 전체 자동 실행을 뜻하지는 않습니다.
